这个文档站是我给自己做的一个作品集。面试或介绍作品时，我希望用一个链接集中展示写过的技术文档、建站过程和工作思考，省去逐个发送文件的麻烦。

{/* truncate */}

## 为什么要搭一个站

介绍技术文档作品时，光看几张截图很难判断文档写得怎么样。读者还需要知道它写给谁、要解决什么问题，以及为什么这样安排内容。我希望别人能直接打开文档，连着前后章节一起看。

之前试过用 Word 或 PDF 展示，但文件比较分散，读者需要逐个下载。在线文档有时要申请权限，访问不够稳定；GitHub README 适合写项目说明，放多篇长文档又不方便。因此，我决定把这些内容整理成一个网站，通过首页和导览页引导读者阅读。

## 我负责的部分

我不是程序员，复杂的配置和页面代码主要由 AI 协助完成。我负责确定站点用途、挑选文档、安排阅读顺序，也负责判断哪些内容需要删除或重写。

搭建时，我先把站点定位为技术文档作品集，将内容分成“文档作品”和“建站手记”。随后用 Docusaurus 搭建基础网站，让 Markdown 文件能作为网页展示，再整理首页和导览页的入口。

内容放上去后，我又加入格式检查和 AI 评分，用来查找格式问题和没有讲清楚的地方。最后将站点部署到 GitHub Pages，让读者可以通过链接直接访问。

## 站点结构

目前站点主要分成四个入口：

| 入口 | 放什么 | 读者能看到什么 |
| --- | --- | --- |
| 首页 | 站点整体介绍和重点卡片 | 快速知道这个站是做什么的 |
| 站点导览 | 所有内容的阅读路径 | 按目标选择先看哪篇文档 |
| 文档作品 | IoT 概念、接入指南、API 文档 | 展示不同类型技术文档的写法 |
| 建站手记 | 建站过程、质量评分、更新流程、工作思考 | 记录站点维护过程 |

文件大致是这样放的：

```text
docs/
├── intro.md              # 站点导览
├── iot-overview.md       # IoT 核心概念
├── iot-platform-guide.md # 小米 IoT 平台接入指南
└── api-docs.md           # IoT 平台 API 文档

blog/
├── 2026-07-01-docs-as-code.md       # 建站过程
├── 2026-07-10-doc-score.md          # 文档质量评估助手
├── 2026-07-14-update-workflow.md    # 文档站更新流程
└── 2026-07-14-iot-doc-thoughts.md   # IoT 文档调研思考
```

这个结构不是一开始就完全想好的，是边写边调整出来的。比如一开始我把“文档调研思考”放在文档作品里，后来发现它更像工作复盘，就挪到了建站手记里。

## 首页和导览页的安排

首页只放简短介绍和几个内容入口。想看技术文档的人可以进入作品集，想了解建站过程的人可以进入建站手记。下面的卡片再介绍各部分的内容，方便读者判断要不要继续看。

文章多了以后，只靠首页上的几个入口还不够。我又单独做了导览页，按阅读目标给出推荐顺序，让读者不用逐篇点开，才能知道哪篇适合自己。

导览页里的“快速选择”用于直接找文档，“站点地图”展示各部分之间的关系，“推荐阅读路径”说明先读什么、再读什么。文档详情表则补充适合读者、主要内容和预计阅读时间，帮助读者安排阅读。

## 文档作品的选择

我挑选了三类文档。IoT 核心概念用来展示如何解释抽象概念；小米 IoT 平台接入指南用来展示如何把长流程拆成可执行步骤；API 文档则展示如何说明接口，让开发者能按需查阅。

这些文档也展示了截图、表格、排障说明和下一步链接的具体用法。例如，操作步骤后需要说明怎样判断成功，概念解释之后需要告诉读者可以继续看什么。

## 建站手记的内容

建站手记记录我在搭站和维护时做过的选择，包括为什么搭站、怎样接入文档质量评分、平时如何更新，以及看完其他平台文档后有哪些改进想法。

我把这类记录和正式的技术文档分开放。读者在文档作品里看写作结果，在建站手记里看我为什么这样组织内容，以及后来根据哪些问题做了调整。
